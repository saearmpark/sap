AI CLI 활용 절차

AI CLI는 터미널에서 대화하듯 코드 수정을 요청하는 도구입니다. 빠르지만, 결과를 그대로 믿으면 안 됩니다. 이 단계에서는 작게 요청하고, 직접 검토하고, 테스트로 확인하고, 커밋으로 남기는 안전한 절차를 익힙니다.

난이도 · 중급 예상 시간 · 30분 준비물 · Node.js, Git, 터미널

1. AI CLI가 하는 일

AI CLI는 프로젝트 폴더를 읽고, 파일을 검색하고, 필요하면 수정안을 제안하거나 적용합니다. 명령을 대신 실행하기도 하므로 권한 범위를 이해하는 것이 중요합니다.

잘하는 일사람이 해야 할 일
반복적인 코드 수정, 파일 탐색, 초안 작성요구사항 결정, 결과 검토, 최종 책임
오류 메시지 해석, 테스트 실행 보조비밀정보 관리, 배포 승인
여러 파일의 일관된 변경실제 화면·동작 확인

2. 시작 전 준비

  1. 프로젝트 폴더에서 터미널을 엽니다. VS Code에서 Ctrl + `를 누르고 Get-Location으로 위치를 확인합니다.
  2. 작업 트리를 깨끗하게 만듭니다. git status로 확인하고, 기존 변경은 먼저 커밋하거나 보관합니다. 그래야 AI가 바꾼 내용과 내 변경을 구분할 수 있습니다.
  3. 되돌릴 수 있게 합니다. 중요한 작업 전에는 브랜치를 하나 만듭니다.
  4. 작업 범위를 정합니다. “사이트 전체 개선” 대신 “manual.html의 모바일 표만 수정”처럼 좁힙니다.
PowerShell 
git status
git switch -c manual-polish

3. AI CLI 실행

이 저장소에서는 opencode를 예로 듭니다. 설치 방법은 opencode.ai의 공식 안내를 따르고, 설치 후에는 프로젝트 루트에서 실행합니다.

PowerShell 
opencode

처음 실행하면 사용할 모델과 권한을 선택합니다. 파일 수정·명령 실행 권한은 필요한 만큼만 허용하고, 낯선 명령은 실행 전에 내용을 확인하세요. 도움말은 /help로 볼 수 있습니다.

TIP

AI가 파일을 찾지 못하면 파일 경로를 직접 알려 주세요. 예: “assets/common.js의 NAV 배열을 수정해 줘.”

4. 좋은 요청의 5요소

  1. 목표 — 무엇을 이루고 싶은가.
  2. 범위 — 어떤 파일·페이지를 바꿀 것인가.
  3. 제약 — 지켜야 할 규칙(기존 스타일, 의존성 추가 금지 등).
  4. 검증 — 어떻게 확인할 것인가(테스트, 화면 확인).
  5. 금지 — 하지 말아야 할 일(커밋 금지, 비밀정보 접근 금지).
좋은 요청 예시 
manual.html의 모바일 목차 카드가 360px에서 글자와 여백이 겹치는 문제를 고쳐 줘.

범위: assets/style.css의 .manual-toc 관련 규칙만.
제약: 기존 색 변수와 클래스 이름을 유지하고, 새 라이브러리는 추가하지 마.
검증: 360px/768px/1280px에서 넘침이 없는지 확인할 수 있게 변경 이유를 설명해 줘.
금지: 커밋과 푸시는 하지 마.
모호한 요청 예시 
사이트 좀 예쁘게 고쳐 줘.

모호한 요청은 범위가 커지고, 검토하기 어려운 대규모 변경이 나오기 쉽습니다.

5. 작업을 작게 나누기

한 번에 여러 기능을 맡기지 말고, 한 요청 = 한 가지 결과로 나눕니다. 예를 들어 메뉴 추가는 다음처럼 나눕니다.

  • 1단계: 공용 메뉴 데이터에 항목 추가
  • 2단계: 새 페이지 골격 생성
  • 3단계: 본문 작성
  • 4단계: 검색·CI 목록 등록
  • 5단계: 검증 및 커밋

각 단계가 끝날 때마다 git diff로 확인하면 문제가 생겼을 때 원인 범위가 좁아집니다.

6. 결과 검토: diff부터 읽기

AI가 “완료했습니다”라고 해도 바로 커밋하지 않습니다. 먼저 무엇이 바뀌었는지 직접 읽습니다.

PowerShell 
git status
git diff
git diff --stat
  • 요청하지 않은 파일이 바뀌지 않았는가.
  • 기존 스타일·이름 규칙을 유지했는가.
  • 삭제된 코드가 정말 불필요한가.
  • 새 의존성·외부 요청이 몰래 추가되지 않았는가.
  • 비밀정보나 개인정보가 들어가지 않았는가.
주의

설명이 그럴듯해도 코드가 맞다는 뜻은 아닙니다. 특히 삭제·덮어쓰기·권한 변경은 반드시 한 줄씩 확인하세요.

7. 테스트와 화면 확인

이 저장소에서 변경 종류에 따라 아래 검사를 실행합니다.

PowerShell 
# 정적 페이지 인라인 스크립트 검사
node .github/scripts/check-inline-scripts.mjs

# Java 변경 시
cd backend-java
mvn test

# 다시 루트로
cd ..

테스트가 통과해도 실제 화면은 따로 확인합니다. Live Server로 페이지를 열고, 메뉴·다크 모드·모바일 폭·콘솔 오류를 봅니다. 가능하면 변경 전후를 나란히 비교하세요.

검증 요청 예시

“수정 후 node .github/scripts/check-inline-scripts.mjs를 실행하고 결과를 알려 줘. 실패하면 원인과 수정안을 제시해 줘.”

8. 커밋으로 남기기

검토와 검증이 끝난 뒤, 사람이 최종 확인하고 커밋합니다. AI에게 커밋을 맡기더라도 메시지와 포함 파일을 직접 확인하세요.

PowerShell 
git add manual.html manual-vscode.html assets/common.js assets/style.css
git diff --cached
git commit -m "Add beginner web production manual"
git push origin main

문제가 생기면 git revert로 되돌릴 수 있도록, 커밋은 작고 목적이 분명할수록 좋습니다.

9. 보안 수칙

  • 비밀정보를 붙여 넣지 않습니다. API 키, DB 비밀번호, 토큰, 주민번호, 고객 데이터는 프롬프트에도 넣지 않습니다.
  • 권한을 최소화합니다. 읽기만 필요한 작업에 파일 삭제·명령 실행 권한을 주지 않습니다.
  • 외부 명령을 확인합니다. curl | sh처럼 내용을 알 수 없는 설치 명령은 실행하지 않습니다.
  • 의존성을 확인합니다. 새 패키지가 정말 필요한지, 신뢰할 수 있는지 확인합니다.
  • 공개 저장소를 기억합니다. 이 저장소는 공개될 수 있으므로 개인 메모·내부 주소를 넣지 않습니다.

10. 멈춰야 할 때

  • AI가 같은 오류를 두세 번 반복해서 고치지 못할 때
  • 요청 범위를 넘어 여러 파일을 크게 바꿀 때
  • 데이터 삭제·마이그레이션·배포 명령을 제안할 때
  • 설명과 실제 코드가 맞지 않을 때

이럴 때는 작업을 중단하고, git diff를 저장해 두고, 더 작은 문제로 나누어 다시 요청합니다. 필요하면 변경을 되돌리고 사람이 직접 수정하는 편이 빠릅니다.

완료 체크리스트

  • 작업 전 git status가 깨끗한 상태를 확인했다.
  • 목표·범위·제약·검증·금지를 포함해 요청했다.
  • 한 번에 한 가지 작업만 맡겼다.
  • git diff로 모든 변경을 직접 읽었다.
  • 검사 스크립트와 실제 화면 확인을 모두 마쳤다.
  • 비밀정보를 프롬프트에 넣지 않았다.
