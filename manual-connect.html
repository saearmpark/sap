웹제작절차 07

제작항목 연결

페이지를 따로 만들었다면 이제 하나의 사이트로 묶을 차례입니다. 이 단계에서는 상대 경로, 공용 메뉴·스크립트, 캐시 버전, PWA 셸·검색·CI 등록까지 이 저장소의 실제 연결 방식을 따라 합니다.

난이도 · 중급 예상 시간 · 25분 준비물 · 새 HTML 페이지

1. 전체 구조 이해하기

이 사이트는 저장소 루트의 정적 HTML을 GitHub Pages로 제공하고, Java API는 Render에서 따로 실행합니다.

HTML/CSS/JS → GitHub 저장소 → GitHub Pages
Java API → Render → /api 응답

따라서 정적 페이지는 파일 경로만 맞으면 서로 연결되고, 게시판·파일·로그인처럼 데이터가 필요한 기능만 API 주소를 사용합니다.

2. 상대 경로 규칙

상황작성 예의미
같은 폴더의 페이지href="news.html"현재 페이지 옆의 파일
공용 스타일·스크립트href="assets/style.css"현재 폴더의 assets 안
루트로 이동href="index.html"사이트 첫 페이지
하위 폴더에서 상위로href="../index.html"한 단계 위 폴더
대소문자 주의

Windows에서는 News.html과 news.html이 같은 파일처럼 보일 수 있지만, GitHub Pages(Linux)는 대소문자를 구분합니다. 링크가 404가 된다면 철자를 확인하세요.

3. 새 페이지 연결 8단계

  1. 파일을 만든다. 저장소 루트에 소문자·하이픈 이름으로 HTML을 만듭니다. 예: manual-server.html.
  2. 공용 골격을 넣는다. 테마 초기화 스크립트, PWA 메타 태그·manifest.webmanifest, assets/style.css, 사이드바, common.js·auth.js·theme.js를 포함합니다.
  3. 메뉴에 등록한다. assets/common.js의 NAV 배열에 항목을 추가합니다.
  4. 검색에 등록한다. search.html의 GROUPS와 staticIndex에 항목을 넣습니다.
  5. PWA 셸에 등록한다. sw.js의 CORE 배열에 페이지와 새로 추가한 공용 자산을 넣습니다.
  6. CI 목록에 추가한다. .github/scripts/pages.txt에 파일명을 한 줄 추가합니다.
  7. 캐시 버전을 올린다. 공용 CSS/JS를 바꿨다면 현재 labels-35을 다음 값인 labels-36로 올리고, sw.js의 캐시 이름도 sap-shell-labels-36로 함께 바꿉니다.
  8. 검증한다. Live Server에서 메뉴·링크·다크 모드를 확인하고, 아래 세 가지 검사와 실제 배포를 확인합니다.

4. 공용 사이드바에 메뉴 추가

이 사이트의 메뉴는 각 HTML에 복사하지 않고 assets/common.js의 NAV 데이터에서 한 번만 정의합니다. 하위 페이지가 여러 개라면 pages 배열에 넣어 메뉴가 활성 상태로 열리게 합니다.

assets/common.js 
{
  label: "학습",
  items: [
    {
      href: "manual.html",
      label: "웹",
      pages: [
        "manual-plan.html",
        "manual-vscode.html",
        "manual-html.html",
        "manual-css.html",
        "manual-javascript.html",
        "manual-python.html",
        "manual-connect.html",
        "manual-server.html",
        "manual-ai-cli.html",
        "manual-finish.html"
      ]
    }
  ]
}

navLink()는 현재 파일명이 href와 같거나 pages에 포함되면 active 클래스를 붙입니다. 메뉴 데이터를 고친 뒤에는 브라우저에서 새로고침해 모든 페이지에 반영되는지 확인하세요.

5. 공용 스크립트로 중복 줄이기

여러 페이지에서 같은 코드를 복사하면 한쪽만 고치는 실수가 생깁니다. 이 저장소는 다음과 같이 역할을 나눕니다.

파일역할
assets/common.js사이드바 메뉴, 테마 토글 버튼 생성, 알림 배지, 공통 유틸
assets/theme.js테마 적용·저장, 모든 토글 버튼 동기화
assets/auth.js로그인 상태·API 요청 공통 처리
assets/feed.js뉴스·시세 등 피드 렌더링
assets/notifications.js알림 목록·읽음 상태 처리
assets/manual.js매뉴얼 코드 블록 복사 버튼
sw.js서비스 워커 — 핵심 페이지 캐시, 오프라인 대체, 버전 정리

한 페이지에서만 쓰는 코드는 해당 페이지의 인라인 스크립트에 두어도 됩니다. 두 페이지 이상에서 쓰기 시작하면 assets/로 분리하세요.

6. 캐시 버전이 필요한 이유

브라우저는 CSS와 JS를 저장해 두고 재사용합니다. 파일을 고쳐도 예전 화면이 보이면 ?v= 값을 올려 새 주소로 인식하게 합니다.

HTML 
<link rel="stylesheet" href="assets/style.css?v=labels-35">
<script src="assets/common.js?v=labels-35"></script>

버전 값은 모든 페이지에서 같은 값을 사용합니다. 한 페이지에만 다른 값을 쓰면 페이지를 이동할 때 CSS가 다시 받아져 깜빡이거나, 반대로 이전 파일이 남을 수 있습니다. 이 사이트는 labels-35을 쓰고 있으므로, 다음에 공용 파일을 고칠 때 labels-36로 함께 올립니다.

서비스 워커의 캐시 이름도 같은 번호를 사용합니다. sw.js의 CACHE 값을 sap-shell-labels-35로 바꾸면, 활성화 단계에서 이전 sap-shell-* 캐시가 자동으로 삭제됩니다. 페이지 버전만 올리고 캐시 이름을 그대로 두면 예전 파일이 계속 남습니다.

TIP

검사 스크립트 check-assets.mjs가 페이지의 ?v= 값과 sw.js의 캐시 이름이 같은지 확인합니다. 둘 중 하나만 고치면 CI에서 바로 실패합니다.

7. 검색 인덱스에 등록

search.html은 정적 항목을 staticIndex에 직접 넣고, 게임·앱 목록은 페이지를 읽어 자동으로 모읍니다. 새 가이드는 아래처럼 제목과 검색어를 함께 넣으면 됩니다.

search.html 
staticIndex.push({
  key: "manual",
  title: "VS Code 설치",
  text: "편집기 설치 Live Server 한국어 확장 개발 도구",
  href: "manual-vscode.html"
});

GROUPS에도 { key: "manual", label: "웹제작절차" }을 추가해야 결과가 올바른 묶음으로 표시됩니다.

8. PWA 셸에 새 페이지 추가

이 사이트는 홈 화면 설치와 오프라인 열기를 지원합니다. 새 페이지도 같은 동작을 하려면 <head>에 PWA 메타 태그를 넣고, 서비스 워커 캐시 목록에 등록해야 합니다.

my-page.html 
<meta name="theme-color" content="#202124">
<link rel="icon" href="assets/icons/icon-192.png" type="image/png">
<link rel="apple-touch-icon" href="assets/icons/apple-touch-icon.png">
<link rel="manifest" href="manifest.webmanifest">

manifest.webmanifest는 사이트 전체가 하나를 공유합니다. 앱 이름·아이콘·시작 주소·바로가기는 이 파일에서 관리하므로, 새 페이지를 추가할 때 수정할 일은 거의 없습니다. 시작 화면 바로가기를 추가하고 싶을 때만 shortcuts 배열에 항목을 넣습니다.

오프라인에서도 열리게 하려면 sw.js의 CORE 배열에 파일을 추가합니다.

sw.js 
const CORE = [
  "./",
  "index.html",
  "offline.html",
  "my-page.html",
  "manifest.webmanifest",
  "assets/style.css?v=labels-35",
  "assets/common.js?v=labels-35"
];
  • 페이지 이동 요청은 네트워크 우선이라, 온라인일 때는 항상 새 HTML을 받고 실패하면 캐시나 offline.html을 보여 줍니다.
  • CSS·JS·이미지는 캐시 우선입니다. 공용 파일을 고쳤다면 반드시 ?v=를 올려야 새 파일이 내려갑니다.
  • CORE에 적은 파일이 없으면 설치가 조용히 넘어갑니다. DevTools Application → Cache Storage에서 실제로 저장됐는지 확인하세요.

확인 방법: DevTools Application → Service Workers에서 Offline을 체크하고 새로고침해 오프라인 페이지가 뜨는지 봅니다. 설치 동작은 주소창의 설치 아이콘(Chrome·Edge) 또는 iOS Safari의 공유 → 홈 화면에 추가로 확인합니다.

9. CI 페이지 목록에 추가

.github/scripts/pages.txt는 모든 검사 스크립트의 기준 목록입니다. 새 페이지를 넣지 않으면 검사 없이 배포되므로 반드시 추가합니다.

.github/scripts/pages.txt 
index.html
manual.html
manual-vscode.html
manual-html.html

로컬에서 미리 검사하려면 저장소 루트에서 아래 명령을 실행합니다.

PowerShell 
node .github/scripts/check-inline-scripts.mjs
node .github/scripts/check-links.mjs
node .github/scripts/check-assets.mjs
검사확인하는 것
check-inline-scripts각 페이지 인라인 스크립트의 문법
check-links루트 HTML이 pages.txt에 모두 있는지, 내부 링크·앵커가 유효한지
check-assets공용 CSS/JS의 ?v= 값이 모두 같은지, sw.js 캐시 이름과 일치하는지
주의

check-links는 루트의 모든 HTML 파일을 검사합니다. 잠깐 만든 테스트 페이지도 pages.txt에 없으면 CI가 실패하므로, 임시 파일은 커밋 전에 지웁니다.

10. 링크·리소스 점검

  • 브라우저 F12 → Network에서 빨간 404가 없는지 확인합니다.
  • 이미지·CSS·JS 경로는 파일명과 대소문자까지 일치해야 합니다.
  • 파일명에 공백이나 한글을 쓰지 않는 것이 배포 후 문제를 줄입니다.
  • 외부 링크에는 rel="noopener"를 함께 사용합니다.
  • 새 메뉴가 모바일에서도 열리고, 키보드 Tab으로 접근되는지 확인합니다.

완료 체크리스트

  • 새 페이지를 루트에 만들고 공용 골격과 PWA 메타 태그를 넣었다.
  • common.js의 NAV에 메뉴를 등록했다.
  • 하위 페이지를 pages 배열에 넣어 메뉴가 활성화되게 했다.
  • 검색의 GROUPS와 staticIndex에 등록했다.
  • sw.js의 CORE에 페이지와 새 자산을 추가했다.
  • pages.txt에 추가하고 세 가지 검사를 통과했다.
  • 모든 페이지의 캐시 버전과 sw.js 캐시 이름을 같은 값으로 맞췄다.
  • 오프라인 새로고침과 홈 화면 설치를 확인했다.
