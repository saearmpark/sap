웹제작절차 08

서버 업데이트

수정한 내용을 인터넷에 반영하는 절차입니다. 이 저장소는 정적 페이지를 GitHub Pages로, Java API를 Render로 배포합니다. 상태 확인 → 검토 → 커밋 → 푸시 → 자동 배포 확인 → 라이브 확인 순서를 지키면 실수를 크게 줄일 수 있습니다.

난이도 · 중급 예상 시간 · 30분 준비물 · Git, GitHub 계정

1. 배포 지도

내 PC 수정 → git commit → git push → GitHub Actions
main 브랜치 → GitHub Pages
backend-java 변경 → Render 자동 배포

정적 페이지는 푸시 후 보통 1~2분, Java API는 2~4분 정도 걸립니다. 배포가 끝나기 전에 접속하면 이전 화면이 보일 수 있습니다.

2. Git과 GitHub 준비

Git for Windows를 설치하면 PowerShell과 VS Code 터미널에서 git을 사용할 수 있습니다. 처음 한 번만 이름과 이메일을 설정합니다.

PowerShell 
git --version

git config --global user.name "내 이름"
git config --global user.email "내 이메일"

# 저장소가 이미 있다면
git status

이미 저장소를 받았다면 git clone은 필요 없습니다. 폴더에 .git이 있는지 확인하세요.

2-1. GitHub 저장소에 처음 올리기

내 컴퓨터에만 있는 웹사이트를 GitHub에 올리는 순서입니다. GitHub에서 New repository를 만들 때, 로컬에 이미 파일이 있다면 README·.gitignore 추가는 체크하지 않습니다.

PowerShell 
git init
git add .
git commit -m "Create first website"
git branch -M main
git remote add origin https://github.com/내아이디/내저장소.git
git push -u origin main
  • git init — 현재 폴더를 Git 저장소로 만듭니다. 이미 .git이 있으면 실행하지 않습니다.
  • git remote add origin ... — GitHub 저장소 주소를 origin이라는 이름으로 연결합니다.
  • 인증 창이 뜨면 브라우저에서 GitHub 로그인을 완료합니다. 비밀번호를 코드에 적지 않습니다.

2-2. GitHub Pages 켜기

저장소에 올렸다고 바로 웹사이트가 열리는 것은 아닙니다. 처음 한 번은 Pages를 켜야 합니다.

  1. 저장소의 Settings → 왼쪽 Pages로 이동합니다.
  2. Build and deployment의 Source를 Deploy from a branch로 선택합니다.
  3. Branch를 main, 폴더를 / (root)로 지정하고 Save를 누릅니다.
  4. Actions 탭의 pages build and deployment가 성공할 때까지 기다립니다.
  5. 표시된 주소로 접속합니다. 주소는 보통 https://내아이디.github.io/저장소/입니다.
중요

Pages 사이트는 공개 주소로 제공됩니다. 비밀번호·API 키·개인정보를 HTML이나 JavaScript에 넣지 마세요. 없는 주소를 위한 404.html을 루트에 두면 안내 페이지를 보여 줄 수 있습니다.

3. 작업 전·후 상태 확인

PowerShell 
git status
git diff
git log --oneline -5
  • git status — 어떤 파일이 바뀌었고, 무엇이 스테이징되었는지 확인합니다.
  • git diff — 아직 스테이징하지 않은 변경 내용을 줄 단위로 봅니다.
  • git log — 최근 커밋 메시지와 순서를 확인합니다.
중요

커밋 전에 git status에 예상하지 못한 파일이 있는지 꼭 확인하세요. 데이터베이스, 업로드 파일, 빌드 결과물, 비밀번호 파일이 섞이면 안 됩니다.

4. 변경 내용 검토

수정한 파일만 골라 스테이징합니다. git add .은 편하지만 불필요한 파일까지 포함할 수 있으므로, 처음에는 파일명을 직접 적는 습관이 좋습니다.

PowerShell 
git diff assets/common.js
git diff --stat

git add manual.html manual-vscode.html assets/common.js assets/style.css
git diff --cached

git diff --cached는 “이번 커밋에 실제로 들어갈 내용”을 보여 줍니다. 여기서 의도하지 않은 변경이 보이면 git restore --staged 파일명으로 뺍니다.

5. 커밋 만들기

이 저장소는 “무엇을 했는지”가 드러나는 짧은 명령형 제목을 사용합니다. 한 커밋에는 한 가지 목적만 담습니다.

PowerShell 
git commit -m "Add beginner web production guide"

# 또는
git commit -m "Fix calendar date contrast in dark mode"

제목은 50자 안팎으로 짧게, 필요하면 본문에 이유와 검증 방법을 적습니다. “수정”, “업데이트”만으로는 나중에 이력을 이해하기 어렵습니다.

6. 원격 저장소로 푸시

PowerShell 
git push origin main

처음 푸시할 때 GitHub 로그인 창이 뜨면 브라우저에서 인증합니다. 비밀번호를 채팅이나 코드에 직접 붙여 넣지 마세요.

TIP

푸시 전에 git pull --rebase로 원격의 최신 변경을 먼저 받아 두면 충돌을 줄일 수 있습니다. 팀 작업이 아니라면 매번 필요하지는 않습니다.

7. GitHub Actions 확인

푸시하면 저장소의 Actions 탭에서 자동 검사가 실행됩니다. 이 저장소의 주요 워크플로는 다음과 같습니다.

워크플로확인하는 것
Java testsmvn test — 게임방 복구, 학습 진도 저장 등
Static site checks공용 스크립트·인라인 스크립트 문법, 페이지 목록과 링크, 공용 자산 버전, sw.js·manifest.webmanifest 형식
pages build and deploymentmain 브랜치의 정적 파일을 GitHub Pages에 배포
Build desktop toolsPyInstaller로 Windows 실행파일 패키징

빨간 X가 뜨면 로그에서 첫 번째 오류를 확인합니다. 로컬에서 같은 검사를 먼저 실행하면 원인을 빠르게 찾을 수 있습니다.

PowerShell 
node .github/scripts/check-inline-scripts.mjs
node .github/scripts/check-links.mjs
node .github/scripts/check-assets.mjs
node --check sw.js
cd backend-java
mvn test

세 가지 정적 검사는 서로 역할이 다릅니다. 인라인 스크립트 문법, 페이지 목록·링크, 공용 자산 버전을 각각 확인하므로 하나라도 건너뛰면 놓치는 오류가 생깁니다.

8. Java API(Render) 업데이트

backend-java를 수정해 푸시하면 Render가 새 버전을 자동으로 빌드·배포합니다. API 주소는 https://board-backend-nngx.onrender.com/api입니다.

  • 환경 변수(DB 주소, 비밀번호, 키)는 코드가 아니라 Render 대시보드에 설정합니다.
  • 배포 로그에서 빌드 실패·헬스 체크 실패가 없는지 확인합니다.
  • 무료 인스턴스는 일정 시간 미사용 시 잠들어 첫 요청이 느릴 수 있습니다.
  • DB 구조나 데이터에 영향을 주는 변경은 배포 전에 백업합니다.

9. 라이브 확인

  1. 캐시를 비웁니다. Ctrl + F5로 새로고침하거나 시크릿 창을 엽니다.
  2. 바뀐 페이지를 직접 엽니다. 메뉴가 아니라 주소로 접속해 404가 아닌지 확인합니다.
  3. 콘솔을 봅니다. F12 → Console에서 빨간 오류가 없는지 확인합니다.
  4. API를 확인합니다. 뉴스·시세·로그인 등 실제 데이터가 필요한 기능을 한 번씩 실행합니다.
  5. 모바일 폭을 확인합니다. 개발자도구의 반응형 모드에서 메뉴와 표가 넘치지 않는지 봅니다.
  6. PWA를 확인합니다. DevTools Application에서 서비스 워커가 activated인지, Offline 체크 후 새로고침해도 offline.html이 뜨는지 봅니다.
  7. 없는 주소를 확인합니다. 404.html을 두었다면 일부러 없는 주소로 접속해 안내 페이지가 나오는지 봅니다.

10. 문제가 생겼을 때 되돌리기

이미 푸시한 커밋을 되돌릴 때는 이력을 지우는 force push 대신, 되돌리는 새 커밋을 만듭니다.

PowerShell 
git log --oneline -5
git revert <되돌릴-커밋-해시>
git push origin main

아직 푸시하지 않은 로컬 변경을 버리려면 git restore 파일명을 사용합니다. git reset --hard는 작업 내용을 완전히 지우므로 습관적으로 쓰지 마세요.

11. 절대 커밋하면 안 되는 것

  • 비밀번호, API 키, 토큰, .env 파일
  • 개인정보가 들어 있는 데이터베이스·업로드 파일
  • target/, build/, dist/, node_modules/ 같은 생성물
  • 다른 사람의 작업을 덮어쓰는 force push
유출됐다면

키를 커밋한 사실을 깨달았다면 먼저 해당 키를 폐기·재발급하세요. 파일을 지우는 것만으로는 Git 이력에 남습니다.

완료 체크리스트

  • git status와 git diff로 변경을 검토했다.
  • 의도한 파일만 스테이징하고 커밋 메시지를 구체적으로 적었다.
  • main에 푸시하고 Actions가 성공한 것을 확인했다.
  • GitHub 저장소를 만들고 Pages를 main / / (root)로 설정했다.
  • Pages와 Render 배포 완료 후 라이브 화면을 직접 확인했다.
  • 정적 검사 세 가지와 sw.js 문법 검사를 통과했다.
  • 서비스 워커 활성화와 오프라인 새로고침을 확인했다.
  • 문제가 생겼을 때 git revert로 되돌리는 방법을 알고 있다.
